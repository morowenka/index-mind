# Анализ лучших практик Docker

## Плохие практики в Dockerfile.bad

1. **Использование последнего/неспецифического базового образа**.
   - Плохо: `FROM python:3.12`.
   - Почему это плохо: образ может работать не так, как ожидается ;).
   - Как исправлено: используется `python:3.9-slim` (та версия, на которой велась разработка)

2. **Многочисленные команды RUN**.
   - Плохо: отдельные RUN-команды для установки зависимостей
   - Почему это плохо: каждый RUN создает новый слой => увеличивается размер образа
   - Как исправлено: объединение команд RUN с помощью && и cleanup

3. **Установка ненужных инструментов**.
   - Плохо: установка vim, nano, git, nodejs и т.д.
   - Почему это плохо: увеличивает размер образа + создает потенциальные уязвимости в безопасности
   - Как исправлено: только необходимые зависимости для сборки

4. **Копирование всей директории**.
   - Плохо: `COPY . .`
   - Почему это плохо: кучу мусора копируем и потенциальные секреты (если, конечно, у нас в .dockerignore не все четко прописано)
   - Как исправлено: копируем только необходимые файлы

5. **Запуск от имени Root**
   - Плохо: нет спецификации пользователя
   - Почему это плохо: банальный риск безопасности - контейнер имеет привилегии root
   - Как исправлено: создан и переключен на nonroot пользователя

6. **Многочисленные порты EXPOSE**.
   - Плохо: expose неиспользуемых портов (8000, 8080, 5000, 3000).
   - Почему это плохо: риск для безопасности и путаница
   - Как исправлено: ставим только необходимый порт 8000

## Хорошие практики в Dockerfile.good

1. **Безопасность**
   - Пользователь без права рута
   - Минимальные зависимости
   - Правильные разрешения на файлы

2. **Оптимизация**
   - Многоступенчатая сборка
   - Комбинированные команды RUN
   - Очистка мусора после установки пакетов
   - Выборочное копирование файлов

3. **Удобство обслуживания**
   - Четкая структура
   - Переменные окружения сгруппированы вместе
   - Реализована проверка здоровья

## Плохая практика использования контейнеров

1. **Хранение постоянных данных внутри контейнеров**.
   - Почему это плохо: данные теряются при удалении контейнера.
   - Решение: монтировать тома для постоянных данных.

2. **Запуск нескольких сервисов в одном контейнере**.
   - Почему это плохо: нарушает принцип единой ответственности
   - Решение: отдельные контейнеры с надлежащей оркестровкой

## Когда не стоит использовать контейнеры

1. **Очень маленькие проекты**
   - накладные расходы на контейнеры могут быть излишними для простых приложений
   - прямое развертывание может быть проще и эффективнее

2. **Приложения с жесткими требованиями к производительности**
    - контейнеры добавляют небольшой уровень абстракции, который может влиять на производительность
    - для приложений реального времени (типа трейдинга) лучше использовать другие решения (монолит)

3. **Когда важна безопасность ядра**
    - контейнеры используют общее ядро операционной системы, что может представлять риск при уязвимости ядра
    - для повышенной изоляции могут быть предпочтительны виртуальные машины или физические серверы
